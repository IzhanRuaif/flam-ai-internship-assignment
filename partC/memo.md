# Decision Memo: Making Outputs More Casual & Conversational ## 1. Recommendation **C. Prompt engineering.** Given the constraints (1x A100-80GB for 2 weeks, one native-speaker reviewer covering Hindi + Kannada only at 10 h/week, 3-week launch review, no external API budget), reviewer bandwidth is the binding constraint, not compute. SFT and the rewriter approach both need labeled training data built first, which would consume most of the reviewer's limited time before any training or evaluation could even start. Prompt engineering needs no training data, ships immediately, and is fully reversible if it fails. ## 2. Assumptions - Average response length: ~150 tokens. - The one available reviewer (native Hindi + Kannada) can evaluate ~40 samples/hour for casualness + meaning preservation. - Reviewer availability: 10 hours/week, for 2 of the 3 weeks before launch review (last week reserved for final checks/rollback decision). - Tamil, Telugu, Bengali, and Marathi have **no native-speaker reviewer available**. These four languages will be evaluated only by an automated/proxy method (e.g. back-translation quality check, or a secondary LLM-as-judge scored against the same casual/formal rubric used for Hindi/Kannada) — not human-validated. - GPU (1x A100-80GB, 2 weeks) is held in reserve, used only if escalation to the rewriter approach is triggered. ## 3. Arithmetic **Reviewer capacity (Hindi + Kannada only, over 2 usable weeks):** reviewer hours = 10 hrs/week x 2 weeks = 20 hours reviewer capacity = 20 hours x 40 samples/hour = 800 samples This capacity covers Hindi and Kannada only. Tamil, Telugu, Bengali, and Marathi get zero human-reviewed samples under this plan. **Day 1 experiment budget:** Day 1 reviewer time = 2 hours (out of the 20-hour budget) Day 1 sample capacity = 2 x 40 = 80 samples (Hindi + Kannada only) ## 4. Success metric **For Hindi and Kannada** (human-reviewed): at least 75% of sampled outputs rated both casual/conversational AND meaning-preserving. **For Tamil, Telugu, Bengali, Marathi** (no native reviewer): at least 75% pass rate on the automated proxy check, treated as a lower-confidence signal, not equivalent evidence to the human-reviewed languages. This is an explicit risk: automated proxy scoring may over- or under-estimate real quality for languages the reviewer cannot personally verify. ## 5. Kill criterion If, after testing 3 prompt variants on an 80-sample Hindi+Kannada batch, no variant reaches 60% dual-pass rate, abandon prompt engineering for those two languages and escalate to the rewriter approach using the reserved GPU budget — this must happen with enough time left before the 3-week launch review to build and test a rewriter, so this check should be completed by end of week 1. Separately: if the automated proxy signal for any of the four unreviewed languages (Tamil, Telugu, Bengali, Marathi) falls below 50% pass rate, do not ship casual-mode output for that specific language at launch — fall back to the current formal output for that language only, rather than shipping unverified quality across all six languages uniformly. ## 6. Day 1 experiment 1. Draft 3 prompt variants for tone. 2. Run each variant against the same ~27 baseline inputs (81 generations) for Hindi and Kannada — the two languages with a real reviewer. 3. Reviewer scores each output pair on two axes: casual tone (yes/no), meaning preserved (yes/no). 4. In parallel, run the same 3 variants once each on a small Tamil/Telugu/Bengali/Marathi sample through the automated proxy check, purely to sanity-check the proxy method itself before relying on it later. 5. Compare Hindi/Kannada results against the 60% kill threshold and 75% success bar; select the best variant or trigger escalation.
